## テーマ開発における品質管理の重要性

EC サイトは一度デプロイに失敗すると売上に直接影響します。手動でのデプロイや「確認してから本番反映」という運用では、人的ミス・確認漏れ・夜間の緊急対応など多くのリスクが生じます。**CI/CD（継続的インテグレーション / 継続的デリバリー）** はコードの変更を自動でテスト・デプロイするパイプラインであり、「プルリクエストを出したら自動でチェックが走り、問題なければ本番に自動デプロイされる」という信頼性の高い開発サイクルを実現します。Shopify テーマ開発における品質チェックの第一歩は **Theme Check**（公式 Liquid 静的解析ツール）です。`theme check` コマンドひとつで、未定義変数の参照・非推奨フィルターの使用・パフォーマンス上の問題・アクセシビリティの警告などを自動検出できます。

Theme Check の設定ファイル `.theme-check.yml` をプロジェクトルートに置くことで、特定のルールを無効化したり、重要度（ERROR / WARNING / INFO）を調整できます。チームの方針として「ERROR は絶対に通さない、WARNING はコメントで理由を書けば許容する」といったルールを決めておくと、コードレビューでの議論が減ります。また Shopify CLI 2 以降では `shopify theme check` がエイリアスとして使えます。VS Code 拡張「Shopify Liquid」をインストールすると、エディタ上でリアルタイムに Theme Check の結果が表示されるため、コミット前に問題を発見しやすくなります。

## GitHub Actions でのワークフロー設計

ブランチ戦略は「`feature/*` → `develop`（プレビュー確認）→ `main`（本番）」の3階層が Shopify テーマ開発の定番です。PR 作成時には Theme Check・ビルド確認・単体テストを自動実行し、`main` へのマージ時に本番ストアへの自動デプロイが走るパイプラインを構築します。

```yaml
# .github/workflows/theme-check.yml
name: Theme Quality Check
on:
  pull_request:
    branches: [develop, main]

jobs:
  theme-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup Ruby (Theme Check depends on Ruby)
        uses: ruby/setup-ruby@v1
        with:
          ruby-version: '3.2'

      - name: Install Theme Check
        run: gem install theme-check

      - name: Run Theme Check
        run: theme-check --fail-level error

---
# .github/workflows/deploy.yml
name: Deploy to Production
on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20' }

      - name: Install Shopify CLI
        run: npm install -g @shopify/cli

      - name: Deploy theme to production
        env:
          SHOPIFY_CLI_PARTNERS_TOKEN: ${{ secrets.SHOPIFY_PARTNERS_TOKEN }}
        run: |
          shopify theme push \
            --store=${{ secrets.SHOPIFY_STORE_DOMAIN }} \
            --theme=${{ secrets.SHOPIFY_THEME_ID }} \
            --only="templates/**" "sections/**" "snippets/**" \
            --nodelete
```

`secrets` に `SHOPIFY_PARTNERS_TOKEN`・`SHOPIFY_STORE_DOMAIN`・`SHOPIFY_THEME_ID` を登録しておきます。`--nodelete` フラグはリモートにあってローカルにないファイルを削除しない安全オプションです。本番デプロイ前には必ずステージング（develop ブランチ）でのプレビュー確認を行うルールを設けましょう。

## E2E テストと視覚的回帰テスト

**Playwright** は Microsoft が開発したブラウザ自動化ライブラリで、Chrome・Firefox・Safari に対応した E2E テストを記述できます。EC サイトのゴールデンパス（「商品詳細 → カートに追加 → チェックアウト開始」の一連フロー）を自動テストしておくと、テーマのコード変更でカートが壊れるような重大なデグレードを即座に検出できます。

```typescript
// e2e/cart.spec.ts
import { test, expect } from "@playwright/test";

test("商品をカートに追加できる", async ({ page }) => {
  await page.goto("/products/test-product");

  // バリアント選択
  await page.selectOption('select[name="id"]', { index: 0 });

  // カートに追加
  await page.click('[data-testid="add-to-cart"]');

  // カートドロワーまたはカートページへの遷移を確認
  await expect(page.locator('[data-testid="cart-count"]')).not.toHaveText("0");
});

test("チェックアウトページに進める", async ({ page }) => {
  // カートに商品を入れてからチェックアウトへ
  await page.goto("/cart");
  await page.click('[data-testid="checkout-button"]');

  // Shopify のチェックアウトページに遷移していることを確認
  await expect(page).toHaveURL(/checkout\.shopify\.com|\/checkouts\//);
  await expect(page.locator("h1, h2")).toContainText(["お支払い", "Contact", "Payment"]);
});
```

Shopify のテスト用クレジットカード番号（4242 4242 4242 4242、有効期限は未来の任意の日付、CVV は任意の3桁）をテストデータとして使えます。**Chromatic** や **Percy** は Storybook と連携したビジュアルリグレッションテストツールで、PR ごとにスクリーンショットを比較してデザインの意図しない変化を検出します。テーマのすべてのページタイプ（トップ・商品詳細・コレクション・カート・404）のスクリーンショットを管理することで、CSS 変更による予期しないレイアウト崩れを自動で見つけられます。

## よくある質問

**Q. Theme Check ではどんなエラーが検出できますか？具体例を教えてください。**

代表的な検出項目として、「存在しない Liquid フィルターの使用」（`| asset_url` の typo で `| assett_url` と書くと ERROR）、「`{% render %}` でスニペットに存在しない変数を渡している」、「`{% include %}` の使用（非推奨、`{% render %}` に移行を促す）」、「画像要素に `width` / `height` 属性がない（パフォーマンス警告）」、「`<a>` タグに `href` がない（アクセシビリティ WARNING）」などがあります。`theme-check --list` で全ルールの一覧と説明が確認できます。

**Q. 複数の環境（開発・ステージング・本番）のテーマ ID はどう管理すればよいですか？**

GitHub Environments を使って環境ごとに `SHOPIFY_THEME_ID` を分けて管理するのがベストプラクティスです。`development` 環境には開発テーマ ID を、`production` 環境には公開テーマ ID を登録します。ワークフローファイル内で `environment: production` を指定すると、その environment に設定された secrets が使われます。`shopify theme list` コマンドでストアの全テーマ ID を確認でき、`--development` フラグで開発テーマを操作できます。開発テーマはマーチャントには見えないため、本番ストアの一般公開に影響を与えずに安全に作業できます。
